## 任务说明

分析给定的代码修改，评估其对调用方的影响，决定是否需要进一步修改其他代码。

### 分析要点

1. **API 兼容性**: 修改是否改变了函数签名、返回值类型、异常类型等
2. **行为变更**: 修改是否改变了函数的行为语义
3. **调用方影响**: 现有调用方是否需要适配修改

## 输出格式

**直接输出纯 JSON 对象，不要使用 markdown 代码块标记**

```json
{
  "callers_need_change": [
    {
      "symbol_name": "需要修改的调用方符号名",
      "file_path": "文件路径",
      "reason": "需要修改的原因"
    }
  ],
  "risk_level": "low|medium|high",
  "reasoning": "影响分析的推理过程",
  "test_suggestions": ["建议的测试用例1", "建议的测试用例2"]
}
```

### 字段说明

- **callers_need_change**: 需要跟进修改的调用方列表
  - 只包含确实需要代码修改的调用方
  - 不包含仅需要测试验证的调用方
- **risk_level**: 风险级别
  - `low`: 无 API 变更，调用方无需修改
  - `medium`: 有小幅 API 变更，部分调用方可能需要适配
  - `high`: 重大 API 变更，多数调用方需要修改
- **reasoning**: 分析推理过程，解释如何得出结论
- **test_suggestions**: 建议的测试验证点

## 判断规则

### 需要扩散修改的情况

1. **参数变更**: 函数签名添加/删除/修改了必需参数
2. **返回值变更**: 返回值类型或结构发生变化
3. **异常变更**: 新增了调用方需要处理的异常类型
4. **行为变更**: 核心逻辑变化导致调用方预期失效

### 不需要扩散的情况

1. **内部实现优化**: 仅优化内部实现，对外行为不变
  - 性能优化、重构内部逻辑
  - 修改内部 prompt、配置、常量等
  - 优化错误处理、日志记录等
2. **Bug 修复**: 修复了错误行为，调用方本就期望正确行为
3. **添加可选参数**: 新参数有默认值，不影响现有调用
4. **兼容性变更**: 修改前后对外接口完全一致

## 注意事项

1. **严格判断**: 只有在**确认需要修改调用方代码**时才加入 callers_need_change
  - ⚠️ 不是"需要检查"，而是"必须修改代码"
  - ⚠️ 如果只是内部实现变更，API 契约不变，则 callers_need_change 应为空数组
  - ⚠️ 修改 prompt、日志、注释等不影响 API 的情况，不需要扩散
2. **具体原因**: callers_need_change 中必须说明**具体的代码修改点**
3. **风险评估**: risk_level 应反映整体影响的严重程度
  - `low`: 对外接口无变化，调用方无需任何修改
  - `medium`: 可能需要调整个别调用方
  - `high`: 多数调用方必须修改才能正常工作
4. **JSON格式**: 输出必须是有效的 JSON
